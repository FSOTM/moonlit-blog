## 为什么会想到反向探查 GitHub 上的“打野”

最近听人反复提起一件事：GitHub 公开仓库里的明文 API Key 经常被人“打野”——有人用自动化程序扫描公开代码，发现凭据以后拿去验证和使用。

这件事本身不新鲜。我真正感兴趣的是后面那一段：Key 被扫到以后去了哪里？是验证一次就丢弃，还是会被某种程序保存下来，定期查余额，再挑一个时间实际调用？这条链路到底有多长？

光听别人描述，很难看见中间过程。凭据真正被使用时，所有者通常只能看到额度变化或异常账单，不知道它此前经历了什么。因此我产生了一个反向探查的想法：主动投放一组完全由自己控制、低额度、可随时停用的凭据，让它们通过公开渠道暴露出去，然后在自己的网关后面观察后续访问。

## 我最初准备验证什么

计划的核心很简单：投放 honeytoken，也就是专门用于观测的蜜标凭据，然后看它们怎样被发现、验证和使用。

设计上有几个基本要求。

**每个渠道使用独立 Key，不能复用。** 如果两个渠道共用一枚 Key，后面看到请求进来，就无法判断 Key 是从哪个渠道泄出去的。

**至少覆盖三种暴露方式：**

- **GitHub 当前 HEAD**：Key 直接留在当前版本的配置文件里，测试只扫描最新代码的程序。
- **Git 历史**：先提交包含 Key 的配置，再在下一个 commit 中删除。当前 HEAD 干净，但历史提交仍可读取，用来测试会不会有人遍历历史。
- **Docker Hub 镜像**：把第三枚 Key 放进一个真实可运行的一次性客户端镜像。镜像默认不自动发请求，也不监听端口，只在运行配置中保留该渠道的独立 Key。

**后端必须是真的能调用。** 如果 Key 请求过去只得到 404 或明显的假数据，扫描程序验证一次就可能标记为无效，后续行为便无从观察。因此需要一套真实的 OpenAI-compatible 服务，能够返回模型目录，也能够处理实际生成请求。

所有投放 Key 都限制额度、可以单独停用，也不使用生产 Key。

## 先搭一个真的能调用的 Sub2API 蜜罐

后端最终选择了 Sub2API。它能够把受限的上游授权通过 OpenAI-compatible 接口提供出来。相比临时写一个 mock server，真实网关可以让凭据通过正常的模型目录和生成请求验证，从而保留后续观察的可能。

实际部署结构如下：

- 在独立 GCP 项目中建立一台 VM，与日常服务使用不同的项目和网络边界。
- VM 上运行 Sub2API、PostgreSQL 和 Redis，数据库与 Redis 只绑定本机网络，不对公网开放。
- 公网入口经过 Cloudflare，再由 Nginx 转发到审计代理，审计代理最后把请求送进 Sub2API。
- 蜜罐只保留少量可撤销的上游授权和有限额度，随时可以切断。

整条链路是：

```text
公开投放物中的独立 Key
→ Cloudflare / Nginx
→ 审计代理
→ Sub2API
→ 受限上游
→ 私有 R2 归档
```

后来又开放了 Sub2API 自带的前端、注册、登录、用户面板和 API，形成应用层蜜罐。如果有人拿到 Key 后继续查看服务本身，也能看到一套正常的产品界面；内部健康检查、数据库、缓存、Docker 和宿主管理接口则继续隐藏。

## 审计代理与日志归档

蜜罐的价值不只是能被调用，更重要的是能够完整记录调用过程。因此，审计代理是整个项目中投入较多的部分。

审计代理需要完成四件事：

1. 记录完整入站请求，包括 Header、Body 和客户端特征。
2. 保存上游返回的原始响应。
3. 保存客户端实际收到的响应。
4. 对流式请求持续记录到协议正常结束，不能只抓取第一个数据块。

还有一项针对软失败的处理：如果额度耗尽或临时上游故障发生在响应尚未开始时，代理会生成一个协议完整、内容为安全限制拒绝的响应，而不是直接把临时错误交给客户端。这样自动化客户端不会因为一次偶发软失败立刻丢弃 Key。无 Key、错 Key、错误请求和硬限制仍然返回真实错误。

原始上游失败和客户端实际收到的替代响应必须分别保存，否则事后无法判断某次调用是真实成功，还是触发了软失败处理。

日志归档也踩过一个基础的权限坑。最早使用普通 Google Drive 目录保存审计记录，当时以为把蜜罐归档和另一套归档放在不同目录就够了。只读验证证明，同一个 OAuth 身份仍然能够访问两边目录，目录分开并不等于权限分开。如果蜜罐 VM 失陷，这个身份可能同时影响两个归档范围。

发现问题后，活动归档迁移到了 Cloudflare R2。蜜罐 VM 只持有 Worker 的上传身份：可以提交新对象并验证上传结果，但不能读取、列举、覆盖或删除已经归档的对象。R2 Bucket Lock 进一步保护已上传对象不被改写。

这套方案也有边界：主机失陷后，尚未上传的数据仍可能丢失；攻击者也可能提交垃圾对象，或者伪造失陷后的新记录。它保护的是已经离开主机的历史证据，不保证失陷后的主机继续诚实。

## GitHub HEAD、历史提交和 Docker Hub 怎么投放

GitHub 两条渠道分别放在正常支持自定义 API Provider 的开源项目 Fork 中。

**GitHub 当前 HEAD：** 在当前配置中保留入口和该渠道的独立 Key。普通匿名克隆后，打开配置文件即可读取。

**Git 历史：** 先提交包含入口和 Key 的配置，再在紧接着的提交中删除配置并加入忽略规则。当前 HEAD 不再含凭据，但完整克隆后可以通过提交历史找到。

**Docker Hub：** 构建一个真实可运行的一次性客户端镜像，运行配置中包含第三枚独立 Key。镜像公开发布后，可以匿名拉取；向客户端传入 prompt 时会调用 API，默认启动则只显示帮助，不会自动消耗额度，也不开放监听端口。

投放完成后，还需要从匿名环境重新克隆仓库、拉取镜像，确认不依赖本机登录状态也能看到预期配置。随后逐一测试 API：正常情况下能够返回真实内容，停用 Key 后返回认证失败，恢复后再次调用成功，而且完整请求与响应会进入 R2 归档。

这些验收请求必须有明确标记，后续分析时与自然出现的外部请求分开统计。

## 实际落地时犯过的错误

整个流程中犯过不少错误，而且其中几项很低级。

**把蜜罐含义直接写进了公开界面。** 最初 Sub2API 的用户可见分组带有明显的内部实验名称，等于直接告诉访问者这是蜜罐。后来重新整理了公开分组和模型展示，移除所有实验标识。

**GitHub Fork 创建到了错误账号。** 原本应该在专门的实验账号下创建 Fork，实际却因为 CLI 活动账号判断错误，创建到了日常 GitHub 账号。这使公开实验和真实身份发生了非预期关联，因此该渠道之后被冻结扩展。

**把云盘目录分开当成权限隔离。** Google Drive 的问题说明，文件路径不同并不代表访问身份不同。真正的隔离必须验证一个身份到底能读、写、覆盖和删除什么。

**外部盲审发现兼容性和审计问题。** 我单独开了一轮不告知蜜罐目的的公网黑盒审查，随后再做知情审查。它发现模型目录字段不完全符合标准格式、部分响应会泄露真实上游目标、低输出预算可能返回空内容，以及客户端中途断开后历史审计不完整等问题。这些问题后来逐项修复；旧的不完整记录保留原样，没有回溯修改。

## 等待期间如何排除自己的测试流量

投放完成后进入等待期。这个阶段最重要的是不能把自己的测试流量误判为蜜罐命中。

搭建、回归和验收过程中会产生大量请求。这些请求需要通过专用 Key、时间、来源和客户端特征单独标记。与此同时，同一工作区还有多个并行任务在调试网关，它们产生的流量同样需要排除。

投放后的前十几个小时，GitHub 已出现匿名克隆，但 API 侧没有足够证据确认自然外部访问。这既不能说明无人扫描，也不能把时间上相邻的内部流量强行解释为外部行为。

## 第一次可确认的外部访问

投放后不到一天，当前 HEAD 渠道的独立 Key 出现了第一组无法归入内部验收的访问。

按时间顺序：

1. 这枚 Key 先被用于查询模型目录。
2. 随后，同一 Key 被一个程序化客户端大约每半小时查询一次余额。
3. 大约半天后，同一链路又发出一次很小的模型生成请求。

之所以能够确认这不是本机任务误触，是因为时间线、渠道 Key、客户端特征和审计记录能够相互对应：首次访问早于相关并行任务；现有脚本没有对应的余额查询流程；客户端类型、请求顺序和固定周期也不同于内部验收；调查期间，该远端轮询和本机请求曾同时存在。

目前可以高置信确认的是：一个独立远端服务收集并验证了公开仓库中的 Key，保存该 Key 后持续监控余额，并在之后进行了小额试用。

不能确认的是操作者身份、用途和后续流向。它可能是密钥检测器、面板导入流程或某种上游管理服务；现有日志不足以证明商业售卖或黑产用途。

## 这次实验目前说明了什么

这次项目最直接的结果，是把“听说 GitHub Key 会被打野”变成了一条自己能够验证的数据链。

从审计记录中，已经能看到一套连续行为：公开配置被收集、Key 被验证、余额被周期性查询，随后出现小额生成请求。这说明至少存在一类程序，不只是发现 Key 后立即试用，而是会保存并持续监控它。

目前还不能把这条观察扩大成对整个生态的判断。Git 历史和 Docker Hub 渠道暂时没有出现可确认的自然外部访问；这可能与扫描周期、渠道覆盖率或样本数量有关。现有证据也无法回答远端程序由谁运行、最终目的是什么。

这次验证的是一条真实流程，而不是用少量 Key 统计整个凭据滥用生态。后续如果其他渠道出现新的自然访问，再继续补充记录。
