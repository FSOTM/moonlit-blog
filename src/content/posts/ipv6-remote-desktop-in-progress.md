> 本文记录从方案选择、故障排查到远程桌面最终连通的过程，仍然保留了中间失败状态。

## 为什么突然需要远程桌面

最近需要出门干活，但正在使用的电脑是一台不能带走的台式机。能带出去的只有一台旧笔记本，所以问题变得很直接：人在外面，怎么回到家里的这台电脑上继续工作？

家里的网络没有公网 IPv4，但有公网 IPv6。第一反应是直接用 IPv6 连 Windows 的 RDP。这个方案看起来最省事：打开 RDP，在路由器和 Windows 防火墙上放行端口，再用一个动态 DNS 域名跟踪经常变化的 IPv6 地址。

但这里有几个实际问题不能跳过：IPv6 地址会变化，Clash 的虚拟网卡可能改写部分网络行为，外出的网络不一定提供 IPv6，而且 RDP 一旦直接暴露到公网，入口本身就变得很明确。

所以这次想解决的不是“怎么打开一个端口”，而是找一个在国内网络环境下能用、地址变化后还能找到主机、并且不把 RDP 直接摊在公网的远程入口。

## 最初的方案其实很简单

最初考虑的是 `DDNS + IPv6 + RDP`：域名指向当前公网 IPv6，旧笔记本解析域名后直接连接 RDP。

IPv6 地址空间很大，随机扫描一个家庭地址并不现实。但动态地址本身不是安全措施。如果域名长期存在，别人可以反复解析域名，再检查常见端口；不需要每次重新扫描整个地址空间。

这并不意味着这个入口一定不能用。个人设备、随机子域名、开启 NLA、使用真正的强密码，再配合只允许必要来源的防火墙规则，风险和公网 IPv4 RDP 不是一个量级。但它仍然是一个直接暴露的 Windows 登录入口，适合临时使用，不适合在没有完整测试的情况下长期打开。

## Tailscale 和 WireGuard 的分歧

随后比较了几种组网方式。

Tailscale 的优点是不用自己维护 DDNS，设备会得到稳定的虚拟地址；它通常优先尝试点对点连接，失败后再走中继。但它的控制面和中继依赖境外服务，在国内是否稳定不能只看宣传，必须在旧笔记本接手机热点后实测 `direct` 还是 `relay`。Clash TUN 也可能干扰它的控制连接和打洞流量。

WireGuard 则更直接：域名只负责找到主机的 UDP 入口，WireGuard 先用密钥建立隧道，RDP 再通过隧道地址连接。这样公网只需要看到 WireGuard 端口，3389 不必直接暴露。

它的问题也很明显：WireGuard 不能解决旧笔记本所在网络没有 IPv6 的问题；动态 IPv6 仍然需要 DDNS；两端配置、密钥、路由和防火墙都要自己维护。它不是“免费多一层就一定更好”，而是用额外配置换取更小的 RDP 暴露面。

在这次场景里，我先倾向于 `DDNS + IPv6 + RDP`，后来又决定把 WireGuard 加进来，尝试让 RDP 只存在于隧道内部。

## 先检查现实环境，而不是直接开端口

真正开始配置前，先检查了台式机当前的状态。

- Windows 版本支持作为 RDP 主机，注册表里的远程桌面开关也已经打开。
- NLA 已开启，但 `TermService` 实际处于禁用状态，3389 没有监听。
- 原有的内置 RDP 防火墙规则范围很宽，一旦服务启动，暴露范围会过大。
- 插电时不会自动睡眠或休眠，因此电源状态不是当前阻断点。
- 主机确实拿到了公网 IPv6，用数字地址访问 IPv6 网络是通的。
- Clash 主要接管 IPv4 默认路由；IPv6 仍从实体网卡出去，但它的 `ipv6: false` 会影响 AAAA 解析。

这一步得到的第一个重要结论是：当时的问题还不是 DDNS，也不是 WireGuard，更不是旧笔记本。RDP 服务根本没有在主机上建立 3389 监听。

旧笔记本刚开始也出现过一次不可达，只是因为当时没有开机。开机后，在同一局域网里从实体网卡测试到它的 3389 是通的，Clash 没有阻断这条局域网连接。

## WireGuard 配置过程比预想中曲折

确认方案后，开始在主机和旧笔记本之间建立 WireGuard 隧道。计划中的结构是：主机使用一个固定的隧道地址，旧笔记本使用另一个地址；公网只接收 WireGuard 的 UDP 端口；RDP 防火墙只允许来自隧道对端的连接。

软件和配置文件放在单独的工作目录中，密钥生成和客户端配置也分开保存。动态 DNS 负责把主机当前的公网 IPv6 写入一个 DNS-only 记录，旧笔记本的 Endpoint 使用域名而不是某一次临时地址。

实际执行时，几次脚本错误让这件事拖得比预想久：Windows 防火墙命令不接受原先写法的全 IPv6 前缀；为了支持失败后续跑，脚本漏掉了状态变量重建；还有一次把没有设置 `$LASTEXITCODE` 的程序调用误判成安装失败。每次发现问题后都先读取实时状态，再精确回滚，避免把半配置的服务和规则留在系统里。

这部分留下的经验很具体：涉及服务、驱动和防火墙时，脚本退出码不能代替实时状态检查；“隧道服务存在”也不能代替“隧道已经握手并且能传输数据”。

## 真正卡住的是 Windows RDP

WireGuard 的排查进行到一半后，问题重新回到了 RDP 本身。`TermService` 可以被启动，但始终没有建立 3389 监听；日志里出现了 RDP 子系统初始化的 `0x80070005`，也就是拒绝访问。

继续检查后，服务权限、服务 SID、相关注册表权限和核心文件签名都没有发现异常。更具体的线索出现在 RDP 证书：证书元数据仍然显示有私钥，但它引用的私钥容器已经不存在。按证书声明的 provider 查询时，密钥容器返回 `0x80090016 NTE_BAD_KEYSET`。

这说明机器上的 RDP 不是单纯“服务没打开”。证书还在，证书对应的私钥却已经丢失或不可访问；尝试让系统重新生成证书也没有成功。修复测试完成后，服务被恢复为禁用，3389 也没有监听，避免在问题没有解决前把入口暴露出去。

## 终于把链路接通

前面的证书、服务和监听器问题处理完以后，远程桌面终于能够通过已经配置好的链路连接。旧笔记本不再需要直接访问公网 3389，而是先进入主机的 WireGuard 隧道，再通过隧道地址访问 RDP。

这次最终验证把之前几个容易混在一起的问题拆开了：

- 公网 IPv6 数据面可用，但地址会变化。
- Clash 会影响 AAAA 解析和部分组网方案的排障，但不是 IPv6 数据面本身的根因。
- DDNS、WireGuard、RDP 是三层不同的问题，任何一层通过都不能代表另外两层通过。
- 真正拖慢进度的是 Windows RDP 子系统和它的证书私钥状态，而不是“IPv6 到底能不能被扫描”。
- WireGuard 的价值也被验证了：公网入口只需要暴露隧道端口，RDP 本身可以限制在隧道内。

这篇先记录到“能够连接”为止。重启后的持久性、换到其他外部网络后的回连、DDNS 周期更新等长期验证，可以在实际使用一段时间后再补回来。现在最重要的结论已经明确：网络入口方案是可行的，真正的问题是主机上的 RDP 早就处于损坏状态；如果一开始不分层检查，很容易把半个小时都浪费在错误的方向上。
