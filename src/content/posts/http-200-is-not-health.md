HTTP 状态码描述的是**当前这次 HTTP 响应**。它不能自动证明数据库可写、鉴权可用、上游返回完整内容，更不能证明用户真正要完成的业务已经成功。

这不是对 `200 OK` 的否定，而是对证据范围的限制。

## 先定义“正常”

开始排查前，先把声称写完整。例如：

> 用户使用有效 API Key 调用目标模型，可以收到完整内容和正常结束事件。

这个定义覆盖了入口、鉴权、调度、上游和响应结束。相比之下，“首页返回 200”只验证了其中很小的一部分。

常见的局部证据包括：

- 容器处于 `running`；
- 本地端口可以建立连接；
- 健康检查返回 200；
- Nginx 能返回静态首页；
- 模型列表中出现了目标名称。

它们都有价值，但不能互相替代。

## 按链路逐层验证

公网应用通常可以拆成下面几层：

```text
DNS → TLS → 反向代理 → 应用 → 数据库或上游 → 完整响应
```

每一层只回答一个明确问题：

| 层级 | 需要确认的问题 |
| --- | --- |
| DNS | 域名是否解析到预期入口 |
| TLS | 证书、域名和加密连接是否正常 |
| 代理 | 请求是否被转发到正确端口和协议 |
| 应用 | 路由、鉴权和参数处理是否正常 |
| 数据或上游 | 真实读写与依赖调用是否完成 |
| 客户端 | 内容是否完整，结束事件是否正常 |

如果某一层已经失败，就先停在这一层收集证据，不需要同时修改后面所有组件。

## 用真实用户路径收尾

最终验证应该尽可能接近用户实际使用方式。API 服务需要使用真实协议、真实认证方式和目标模型；内容站点需要打开实际文章、资源和导航。

完成声明也必须与验证范围对应：只检查了健康接口，就只能说健康接口正常；跑通完整业务路径后，才能说这条路径可用。
